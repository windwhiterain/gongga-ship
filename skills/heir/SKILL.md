# 立即开始培养继承人

这个服务端**不替你压缩**。它只测量，到阈值发一条 `Context notice`。这意味着**现在开始培养继承人**，不是先把当前工作做完。

不需要先 commit、整理 git、让测试通过或留下干净状态。未提交的修改、失败的测试、正在运行的命令都可以是继承人接着工作的起点；把真实状态和下一步写清楚，直接运行 `heir`。

上下文是**你**的工作记忆。培养继承人不是结束工作，而是让工作换一副更大的工作记忆继续：原文由 mentor 保存，当前会话成为继承人，只带着你的第一课继续前进。

| | `heir` |
|---|---|
| 做的事 | 全份存进 mentor → 校验 → **删空当前会话**（留在飞的那个 call）→ 用 `send_message` 把第一课发给自己 |
| 原文还在当前会话吗 | 不在，完整副本在 mentor 会话里 |
| 继承人下一次请求发什么 | 你这条 call 和它的结果、第一课这条消息，就这些 |

## 开始培养

```bash
# 从本 skill 的目录运行：`@skill:` 展开里是 `@skill: <名字> (<path>)`，取 `<path>` 的父目录；
# gongga 里更短：`gongga-cli skill heir read`。
SKILL_DIR=<本 SKILL.md 所在目录>
T="$SKILL_DIR/transcript"

# 可选：只有需要回顾对话时才先读；收到 Context notice 不要先做收尾工作
$T read

# 给继承人的第一课：当前目标、试过什么、成败、当前状态、下一步
$T heir --note "<继承人的第一课>"
```

**没有 `--session`。** 会话是谁，脚本从 `GONGGA_SESSION` 读——那是服务端给每个会话的每个 shell 注入的。一条会删行的命令不该接受"我清的是谁"这种说法：能自己指定会话名的调用方，就能清空别人的 transcript，再多的名字检查都不如把这个参数去掉。

`--mentor` 省略就是 **`<你的会话名>/mentor`**，而且**必须**在你自己的路径下（`<你的会话名>/…`），否则拒绝。所以：

- `main` 的第一份档案在 `main/mentor`，第二份在 `main/mentor/2`——**不会**续进同一份 archive。理由是继承人要用 `get_messages --session <mentor> 1:` 读回全部原文，两代档案串在一个会话里，它分不出哪一段是自己的过去、哪一段是上一代的。
- `heir --mentor @monitor` 或 `--mentor other/x` 一律拒绝：档案是"造它的那个会话的子节点"，这条规则是结构性的，不需要脚本知道哪些名字是保留的。`@monitor` 自己被叫去培养继承人时，档案落在 `@monitor/mentor`，仍然是它自己名下。

mentor 不存在就用当前的 model 和 cwd 建一个；它是普通会话，之后能用 `get_messages` 读、用 `send_message` 问。

`read` 读的是**对话本身**：模型说的话和注入的消息。每条带 `seq`、`role`、`chars`、`text`；工具调用、工具结果、reasoning 被过滤。默认读最后 40 条、给全文。需要回顾时才用它，不要为了形式上的完整推迟培养继承人。

| 参数 | 用处 |
|---|---|
| `--after` | 默认从最早开始；给一个 seq 只看它之后的 |
| `--limit` | 默认 40 条消息 |
| `--preview` | 每条只给前 120 字符，用来看形状 |
| `heir` 之后 | 指引就在这条命令的结果里；mentor 也会收到一条说明自己职责的 tool_result |

## 继承人先读，再问

清空之后没有隐藏的边界：指引就在 `heir` 命令的结果里，第一课则是脚本用一次 `send_message` 发的普通消息，在下一个 step 边界落成一条 user 行。当前会话留下这个 call 和它的结果，provider 才能接受下一次请求。

第一课走 `send_message` 而不是写进数据库，有两个原因：一，它现在就在这条 call 里跑，直接插一行会落在 call 和它的结果之间，那是 provider 不收的形状；二，一条普通消息才会被当作**空会话的首条 user 消息**处理——它命名的 `@file:`/`@skill:` 因此进 index、随前缀缓存只收一次费（机制、拼法和写错的后果见 `@skill:prefix-cache`）。别把它改回某种"笔记列"，那正是这条路原来的样子。

```bash
gongga-cli get_messages --session <你的会话名>/mentor 1:
gongga-cli send_message <你的会话名>/mentor "…"
```

**先读。** 做过什么、决定过什么、哪次失败为什么失败都在原文里；`get_messages` 不走模型、不花额度。

**再问。** 只有问题需要判断时才发消息，例如“当时该不该选 X”。一次 `send_message` 就是一个真实回合，mentor 的上下文也会增长；它收到自己的 `Context notice` 时，同样开始培养下一代继承人。

## 为什么删之前要校验

`heir` 在一个事务里：追加到 mentor → 逐行比对 `(kind, content, display, call_id)` → 才删。任何一行对不上就整体回滚，当前会话不会先空。

## 为什么这是一个脚本而不是服务端工具

它只做两件事：`read` 一条 SELECT；`heir` 是一个事务里的 INSERT + 校验 SELECT + DELETE，事务提交之后再用 `send_message` 把第一课发给自己。是否培养继承人由最了解当前工作的 agent 决定，脚本只负责可靠地保存原文和准备继承人的起点。

## 继承人的第一课写什么

写给**继续当前工作的继承人**。它下一次请求只有这份笔记，没有当前会话的原文。

要它读的东西**写成引用**，别写成一串路径：`@file: docs/notes/plan.md` 会让正文自动进
index（第一课是空会话的第一条消息），写 `docs/notes/plan.md` 只会让它再花一次 bash 去读。
值必须是一个词、后面要有空白，否则引用静默失效——细则见 `@skill:prefix-cache`。

必须写清：

- 用户到底要什么，包括约束、边界、不许改什么
- 试过什么、什么成了、什么失败，以及失败原因
- 当前文件、进程、分支和测试的真实状态；未提交、未清理、未全绿都如实写
- 还没做完的事和**下一步动作**
- 后续容易踩坑的决定，例如“不要用 X，因为 Y”

可以省略原始命令输出、文件全文、读过的长文档和重复失败；需要保留时写路径和结论。不要只写“上面讨论了 X”，因为继承人的下一次请求里没有“上面”。

## 什么时候开始培养

- **收到 `Context notice`：现在。** 不以“快做完了”“还没 commit”“测试还没绿”为理由推迟。
- 一大段探索结束，结论已经写进第一课，旧过程不再值得占工作记忆。
- 工作要换方向，旧方向的原文仍有查阅价值，但不该继续占据当前上下文。

## 什么时候不必培养

- 刚开始，还没有值得保存的过程，也没有收到 `Context notice`。
- 只是想“每次少发一点”。`heir` 会移走整段原文，不是逐条裁剪工具结果的工具。

## 硬规矩

- **`--note` 不能空**：原文在 mentor，继承人每次真正带着的是第一课。
- **第一课发不出去就整体报告出来**：会话此时已空，脚本会把第一课原样写进结果（也就是这条 call 的 tool_result）并非零退出。那不是丢课，是换了个位置存。
- **第一课里的引用要用 `@file:`/`@skill:`**，而且值是一个词：它是整份 transcript 被清空之后唯一的一条消息，写对了只付一次费，写错了模型只能自己再去读。
- **不需要 clean state**：不要先修复、提交、清理或验证再运行命令；当前状态本身就是课程内容。
- **`heir` 之后 `seq` 从 1 重新开始**（没有在飞的 call 时），第一课就是第 1 行；没有隐藏边界，也没有"笔记列"。不要自己手写 SQL 动这张表。
- **不要频繁培养**：每次都要重新写第一课；但收到新的 `Context notice` 时仍应立即行动。
- 图片的 provider 侧 `file_id` 随原行走；继承人需要再次发送同一张图时要重新上传。
- 成功后 `context_tokens` 归零是正常的，下一次请求会重新测量。

## 验证与发布门禁

修改 `transcript.py` 后，在 server 仓库根目录运行：

```bash
scripts/heir_selftest.sh
```

它从 `crates/server/src/store.rs` 抽取当前 `SCHEMA`，让检查在真实 server schema 上运行，而不是只信脚本自己的最小 fixture。`scripts/ship.sh` 正式发布前会自动运行这道门禁。

## 留下了什么记录

`heir` 成功后往 `events` 表写一条 `kind = 'handover'`：机制、mentor、行数、seq、在飞的 call、第一课字数、当时的 `context_tokens` 和 `context_limit`。这是记录，不是决定请求内容的事实来源；写入失败只报告 stderr，不让已经成功的培养过程回滚。
