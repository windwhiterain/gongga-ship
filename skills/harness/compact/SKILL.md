# 折叠自己的上下文

这个服务端**不再替你压缩**。它只测量，到阈值时给你发一条 `Context notice`，然后等你决定。

上下文是**你**的工作记忆。谁最清楚哪一段还需要、哪一段已经榨干了？只做了一个工具调用就扔掉全部，和什么都不扔，都错。

## 两步

```bash
T=$GONGGA_HOME/skills/compact/transcript.py

# 1. 看：哪些消息还在被发送
$T read --session <你的会话名>

# 2. 折：把 upto 之前的一切换成一份交接笔记
$T collapse --session <你的会话名> --upto 42 --summary "..."
```

`read` 读的是**对话本身**：模型说的话、以及被注入进来的消息。每条带 `seq`（`collapse`
要的就是它）、`role`、`chars`、`text`。**工具调用、工具结果、reasoning 全部过滤掉**——
它们占了 transcript 八成以上的行，却不是你要读的东西。

默认 40 条消息、给全文（约 3k tokens）。这才是交接笔记的材料来源。

| 参数 | 用处 |
|---|---|
| `--after` | 默认从 `summarised_upto` 之后，即当前正在发送的那段；`0` 从最早开始（捞折叠掉的） |
| `--limit` | 默认 40 条消息 |
| `--preview` | 每条只给前 120 字符，用来看形状 |

### 为什么是脚本而不是内置工具

因为它只是数据库上的几条 SQL：`read` 一条 SELECT，`collapse` 两条 UPDATE。做成服务端工具
意味着改一行读取策略就要重新编译、重启服务端、取消正在跑的回合——代价远超收益。

## 交接笔记写什么

写给**下一轮的自己**，那个自己只有这份笔记、没有原文。

要留下：

- 用户到底要什么（原话里的约束、边界、不改什么）
- 试过什么、什么成了、什么失败**以及为什么失败**
- 现在文件/进程/分支处于什么状态
- 还没做完的事，以及下一步
- 任何后面会踩坑的决定（"不要用 X，因为 Y"）

可以扔：原始命令输出、文件内容、读过的长文档、重复的失败重试、已经落盘到文件里的东西（**指个路径就行**）。

不要写"上面讨论了 X"——上面已经不在请求里了。

## 什么时候该折

- 收到 `Context notice`：那是唯一明确的信号，说明上次请求的 token 数已经越过阈值。
- 你开始重复读同一批文件/同一段输出，说明旧内容已经没有增量价值。
- 一大段探索结束了，结论已经明确：把结论写进笔记，把过程扔掉。

## 什么时候不该折

- 活儿快完了。折一次的代价是一份笔记 + 一次判断，收益只有几步。
- 你还在那一段里。折掉自己正在用的证据，下一轮就得重新查一遍——**那比重读更贵**。
- 刚开始。没有可扔的东西时折叠只是噪声。

## 硬规矩

- **被折叠的行没有消失。** 数据库里全在，`transcript.py read --after 0` 或直接查库都读得到。折的是"发送什么"，不是"记住什么"。
- **不要自己拼一份假 summary** 来省 token。笔记是给下一轮自己的唯一事实来源，写假的等于自欺。
- **一次折一大段，不要频繁小折。** 每次折叠都要重写整份笔记；折 5 次就是写 5 遍。
- 折完 `context_tokens` 归零是正常的：那个数字量的是**刚被折掉的那个前缀**，下一次请求会重新测。

## 为什么是这样

内置压缩会在阈值处直接调一个模型去总结。问题是那个模型没做过这些活：它不知道哪个失败是关键的，哪个输出后面还要用。把决定交回给拥有上下文的人，代价是你要主动做这件事——`Context notice` 就是提醒。
