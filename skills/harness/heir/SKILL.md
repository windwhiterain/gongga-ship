# 把上下文交接出去

这个服务端**不替你压缩**。它只测量，到阈值时给你发一条 `Context notice`，然后等你决定。

上下文是**你**的工作记忆。谁最清楚哪一段还需要、哪一段已经榨干了？只做了一个工具调用就扔掉全部，和什么都不扔，都错。

两条路，成本完全不同：

| | `collapse` | `heir` |
|---|---|---|
| 做的事 | 把 `--upto` 之前换成一份笔记 | 全份拷进 mentor → 校验 → **删空自己** → 注入引导 |
| 行还在库里吗 | 在，`read --after 0` 读得回来 | 不在，唯一的完整副本在 mentor 会话里 |
| 下一次请求发什么 | 笔记 + `--upto` 之后的原文 | 笔记 + 引导那一条，就这些 |
| 什么时候选它 | 你还在附近，可能得回头看原文 | 那一段真的结束了，你想让眼前彻底干净 |

## 三步

```bash
T=$GONGGA_HOME/skills/heir/transcript

# 1. 看：哪些消息还在被发送（工具调用/结果/reasoning 已被过滤）
$T read --session <你的会话名>

# 2. 写：交接文档——下一轮的你唯一的事实来源（清单见下面那节）

# 3. 交：整份 transcript 进 mentor，然后清空自己
$T heir --session <你的会话名> --mentor mentor-<你的会话名> \
        --note "<交接文档>"
```

`--mentor` 是**任意一个会话名**，不存在就建一个（沿用你现在的 model 和 cwd）。它就是一条普通会话，
所以之后能用 `get_messages` 读它、用 `send_message` 问它——没有专门的机制要学。

`read` 读的是**对话本身**：模型说的话，以及被注入进来的消息。每条带 `seq`（`collapse` 要的就是它）、
`role`、`chars`、`text`。**工具调用、工具结果、reasoning 全部过滤掉**——它们占了 transcript 八成以上
的行，却不是你要读的东西。默认 40 条、给全文（约 3k tokens），这才是交接笔记的材料来源。

| 参数 | 用处 |
|---|---|
| `--after` | 默认从 `handover_upto` 之后，即当前正在发送的那段；`0` 从最早开始（捞折叠掉的） |
| `--limit` | 默认 40 条消息 |
| `--preview` | 每条只给前 120 字符，用来看形状 |
| `heir --guide` | 替换注入的那条引导消息（默认那条带上 mentor 名字和两条现成命令） |

### 先读，再问

清空之后 `heir` 会往你的会话里插进一条引导消息，里面带着 mentor 的名字和两条命令：

```
读档案： gongga get_messages --session mentor-main --range 1:
问一句： gongga send_message --session mentor-main --message "…"
```

**先读。** 你做过什么、决定过什么、哪次失败为什么失败——那些都在行里，记录比任何模型的回答都准，
而且 `get_messages` 不走模型、不花额度。

**再问。** 只有当问题是个判断（"当时该不该选 X"、"这个报错说明什么"）才发回合——mentor 手里有完整的
来往，你手里只有摘要。代价要说清楚：一次 `send_message` 就是一个真回合，花额度，mentor 自己的上下文
也会长；它要是也快满了，你同样能给它跑 `heir --session mentor-main --mentor mentor-main-2`。

### 为什么删之前要校验

`heir` 在一个事务里：追加到 mentor → 逐行比对 `(kind, content)` → 才删。任何一行对不上就整体回滚，
你会话里的行一条都不会少。所以"档案没建成、自己先空了"这个最坏情况不会发生。

### 为什么这是一个脚本而不是服务端工具

因为它只是数据库上的几条 SQL：`read` 一条 SELECT，`collapse` 两条 UPDATE，`heir` 是一个事务里的
INSERT + 校验 SELECT + DELETE。做成服务端工具意味着改一行拷贝策略就要重新编译服务端、换手、取消正在
跑的回合——代价远超收益。（校验和删除必须同事务，这条恰恰是脚本给的红利。）

## 交接笔记写什么

写给**下一轮的自己**，那个自己只有这份笔记、没有原文。

要留下：

- 用户到底要什么（原话里的约束、边界、不改什么）
- 试过什么、什么成了、什么失败**以及为什么失败**
- 现在文件/进程/分支处于什么状态
- 还没做完的事，以及下一步
- 任何后面会踩坑的决定（"不要用 X，因为 Y"）

可以扔：原始命令输出、文件内容、读过的长文档、重复的失败重试、已经落盘到文件里的东西（**指个路径就行**）。

不要写"上面讨论了 X"——`heir` 之后不只在请求里没有了，在你的会话里也没有了；要留就留路径和结论。

## 什么时候该交

- 收到 `Context notice`：那是唯一明确的信号，说明上次请求的 token 数已经越过阈值。
- 一大段探索结束了，结论已经写进笔记：过程进档案，眼前该空了。
- 任务要换方向：旧方向的上下文对新方向是噪声，但可能还要回看——那就交给 mentor，别直接删。

## 什么时候不该交

- 活儿快完了。交接的代价是一份笔记 + 一次判断，收益只有几步。
- 你还在那一段里。把正在用的证据交走，下一轮就得重新查一遍——**那比重读更贵**。
- 刚开始。没有可扔的东西时交接只是噪声。
- 你其实只想"留着行但不发"：那是 `collapse`。`heir` 删掉的行**回不来**（只有 mentor 里有）。

## 硬规矩

- **`--note` 不能空**，脚本会拒绝：档案在 mentor，但你每轮真正发出去的是这份笔记。
- **`heir` 之后 `seq` 从 1 重新开始**，`handover_upto` 归 0——不然第一条新消息会被当成"已经折掉"，
  永远发不出去。脚本已经处理，别自己手写 SQL 去动这两列。
- **一次交一大段，不要频繁小交。** 每次都要重写整份笔记；交 5 次就是写 5 遍。
- 图片的 provider 侧 `file_id` 是随行一起走的：清空之后要再发那张图，得重新上传（脚本不管这件事）。
- **不要自己拼一份假笔记** 来省 token。笔记是唯一事实来源，写假的等于自欺。
- 交完 `context_tokens` 归零是正常的：那个数字量的是**刚被交掉的那个前缀**，下一次请求会重新测。

## 为什么是这样

内置压缩会在阈值处直接调一个模型去总结。问题是那个模型没做过这些活：它不知道哪个失败是关键的，哪个
输出后面还要用。把决定交回给拥有上下文的人，代价是你要主动做这件事——`Context notice` 就是提醒。

而"清空"这件事一直没人肯做，是因为删了就回不来。现在回得来的地方就是一条普通会话：不用新命令、不用
文件同步协议，`get_messages` 和 `send_message` 本来就在。

改 `transcript.py` 之后跑 `python3 test_heir.py`：它在临时目录里造一份最小 schema 的数据库，
不需要服务端、不花额度，专测那条破坏性路径——副本对不上就必须整体回滚。
服务端那边的理由见 `docs/notes/server-handover.md`（只在服务端仓库里有）。
