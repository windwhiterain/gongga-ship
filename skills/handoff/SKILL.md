# 交接上下文（handoff）

这个服务端**不替你压缩**。它只测量，到阈值发一条 `Context notice`。这意味着**尽快交接（handoff）**——但不是立刻砍断，也不是先把当前工作做完。先把交接材料整理好，再运行 `handoff`。

交接不是结束工作，而是让工作换一副更大的工作记忆继续：原文由 mentor 保存，当前会话清空，只带着你的交接笔记继续前进。上下文是**你**的工作记忆；交接之后还是**你**在做这件事，只是不再背着整段原文。

| | `handoff` |
|---|---|
| 做的事 | 全份存进 mentor → 校验 → **从尾部剪空当前会话**（在飞的 call 剪掉再 append 回来）→ 用 `send_message` 把交接笔记发给自己 |
| 原文还在当前会话吗 | 不在，完整副本在 mentor 会话里 |
| 下一次请求发什么 | 你这条 call 和它的结果、交接笔记这条消息，就这些 |

## 先整理，再交接

收到 `Context notice` 后，**不要立刻运行命令，也不要开新活**。先把只有你脑子里才有的东西落到纸面，让接手的一方（也就是清空后的你自己）拿到的是一份整理好的材料，而不是一句“上面讨论过 X”：

- **提交 WIP、整理 git 状态**：未提交的改动先 commit，让接手的上下文继承的是一个被记录下来的状态，而不是随时会丢的工作区。
- **写下历史与记忆**：当前目标、试过什么、什么成了什么失败、失败原因、文件/进程/分支/测试的真实状态、下一步动作。这些原文里没有，只有你知道。
- **整理文档与引用**：把接手方需要读的文档、笔记归拢好，在笔记里用 `@file(...)`/`@skill(...)` 点名（见下）。

不需要先把任务做完、让测试全绿或修复失败——**未完成和失败本身就是真实状态**，如实记录，而不是先修好再交接。整理是为了交得清楚，不是为了收尾。

## 运行交接

```bash
# 从本 skill 的目录运行：`@skill(...)` 展开里是 `@skill(<名字>) (<path>)`，取 `<path>` 的父目录；
# gongga 里更短：`gongga-cli '{"name":"run_skill","args":{"id":"harness/handoff","cmd":{"args":["read"]}}}'`。
SKILL_DIR=<本 SKILL.md 所在目录>
T="$SKILL_DIR/transcript"

# 可选：需要回顾对话时才读
$T read

# 交接笔记：当前目标、试过什么、成败、当前状态、下一步
$T handoff --note "<交接笔记>"
```

**没有 `--session`。** 会话是谁，脚本从 `GONGGA_SESSION` 读——那是服务端给每个会话的每个 shell 注入的。一条会删行的命令不该接受"我清的是谁"这种说法：能自己指定会话名的调用方，就能清空别人的 transcript，再多的名字检查都不如把这个参数去掉。

`--mentor` 省略就是 **`<你的会话名>/mentor`**，而且**必须**在你自己的路径下（`<你的会话名>/…`），否则拒绝。所以：

- `main` 的第一份档案在 `main/mentor`，第二份在 `main/mentor/2`——**不会**续进同一份 archive。理由是接手方要用 `get_messages --session <mentor> 1:` 读回全部原文，两代档案串在一个会话里，它分不出哪一段是自己的过去、哪一段是上一代的。
- `handoff --mentor @monitor` 或 `--mentor other/x` 一律拒绝：档案是"造它的那个会话的子节点"，这条规则是结构性的，不需要脚本知道哪些名字是保留的。`@monitor` 自己被叫去交接时，档案落在 `@monitor/mentor`，仍然是它自己名下。

mentor 不存在就用当前的 model 和 cwd 建一个；它是普通会话（档案），之后能用 `get_messages` 读、用 `send_message` 问。

`read` 读的是**对话本身**：模型说的话和注入的消息。每条带 `seq`、`role`、`chars`、`text`；工具调用、工具结果、reasoning 被过滤。默认读最后 40 条、给全文。需要回顾时才用它。

| 参数 | 用处 |
|---|---|
| `--after` | 默认从最早开始；给一个 seq 只看它之后的 |
| `--limit` | 默认 40 条消息 |
| `--preview` | 每条只给前 120 字符，用来看形状 |
| `handoff` 之后 | 指引就在这条命令的结果里；mentor 也会收到一条说明自己职责的 tool_result |

## 交接之后：先读，再问

清空之后没有隐藏的边界：指引就在 `handoff` 命令的结果里，交接笔记则是脚本用一次 `send_message` 发的普通消息，在下一个 step 边界落成一条 user 行。当前会话留下这个 call 和它的结果，provider 才能接受下一次请求。

交接笔记走 `send_message` 而不是写进数据库，有两个原因：一，它现在就在这条 call 里跑，直接插一行会落在 call 和它的结果之间，那是 provider 不收的形状；二，一条普通消息才会被当作**空会话的首条 user 消息**处理——它命名的 `@file(...)`/`@skill(...)` 因此进 index、随前缀缓存只收一次费（机制、拼法和写错的后果见 `@skill(prefix-cache)`）。别把它改回某种"笔记列"，那正是这条路原来的样子。

```bash
gongga-cli '{"name":"get_messages","args":{"session":"<你的会话名>/mentor","range":"1:"}}'
gongga-cli '{"name":"run_skill","args":{"id":"harness/self-control","cmd":{"args":["ask","<你的会话名>/mentor","<你的问题>"]}}}'
```

**先读。** 做过什么、决定过什么、哪次失败为什么失败都在原文里；`get_messages` 不走模型、不花额度。

**必须问，不要重做。** 要动手之前先问 mentor 一句：它手上有整份原文，包括那些你已经不记得的失败和它们失败的原因。问一句是一个回合，重新摸索一遍是把整场搜索再付一次——上下文就是这么没的。

上面第二条就是问它的命令（`self-control` skill 的 `ask`）：**会话名在前，问题在后**，
问完它替你等，答复直接印在 stdout。它之所以把会话名放前面，是因为 `send_message` 的位置参数
是 `--message` 在前——照抄那个顺序会把会话名当成问题发出去。

问的时候把问题说具体：**要什么答案、为什么现在要**。"当时能不能这么写"这种问法只能换来一句"能"，把你卡住的那一步写进去，才有东西可答。

答案也会以一条消息回到你当前会话里：继续做你的事，消息到了再读。

一次 `send_message` 就是一个真实回合，mentor 的上下文也会增长；它收到自己的 `Context notice` 时，同样先整理再交接下一代。

## 为什么删之前要校验

`handoff` 在一个事务里：追加到 mentor → 逐行比对 `(kind, content, display, call_id)` → 才剪。任何一行对不上就整体回滚，当前会话不会先空。

上下文只有 **append/cut** 两种操作，且 cut 只能从尾部剪（服务端 `context_cut_tail_only` 触发器挡住任何剪掉非最新行的删除）。所以原 transcript 是从最新一行往回逐行剪掉的；在飞的那个 call 本身就是尾部，会随历史一起被剪掉、再原样 append 回来——`call_id` 不变，服务端随后写的 result 靠它配对——落在 seq 1。

## 为什么这是一个脚本而不是服务端工具

它只做两件事：`read` 一条 SELECT；`handoff` 是一个事务里的 INSERT + 校验 SELECT + DELETE，事务提交之后再用 `send_message` 把交接笔记发给自己。是否交接由最了解当前工作的 agent 决定，脚本只负责可靠地保存原文和准备接手方的起点。

## 交接笔记写什么

写给**继续当前工作的你自己**（清空后的会话）。下一次请求只有这份笔记，没有当前会话的原文。

要读的东西**写成引用**，别写成一串路径：`@file(docs/notes/plan.md)` 会让正文自动进
index（笔记是空会话的第一条消息），写 `docs/notes/plan.md` 只会让它再花一次 bash 去读。
括号别漏，漏了引用静默失效——细则见 `@skill(prefix-cache)`。

必须写清：

- 用户到底要什么，包括约束、边界、不许改什么
- 试过什么、什么成了、什么失败，以及失败原因
- 当前文件、进程、分支和测试的真实状态；未提交、未清理、未全绿都如实写
- 还没做完的事和**下一步动作**
- 后续容易踩坑的决定，例如“不要用 X，因为 Y”

可以省略原始命令输出、文件全文、读过的长文档和重复失败；需要保留时写路径和结论。不要只写“上面讨论了 X”，因为下一次请求里没有“上面”。

**结论必须站得住，否则写成“未结案”。** 接手方拿到的是一份结论清单，它不会回头怀疑——
一条写错的“已查明”会让它跳过本来必须继续追的问题。四条判据：

- 写“已查明/已确认”时，同一段里必须跟着**可复现的观测**：哪条命令、输出是什么、第几行、
  多少条。没有观测支撑的判断一律写“未结案”，不要因为“看起来是这么回事”就结案。
- 未结案的问题单独一节 `## 未结案（接手方继续查）`，每条写清**判据**：查什么、什么算查清。
  没有判据的“待查”等于没有交出去。
- 现象和结论分开写。“补丁为空、模型自称完成”是现象；“所以是环境的问题”是结论。
  没有证据时只写现象。
- 用户没有确认过的结论不要写成已定案；写“我的判断（未确认）”，并写清下一步怎么验证。

## 什么时候交接

- **收到 `Context notice`：尽快。** 先整理好交接材料再运行，不立刻砍断，也不以“还没整理完”为由无限推迟。
- 一大段探索结束，结论已经写进笔记，旧过程不再值得占工作记忆。
- 工作要换方向，旧方向的原文仍有查阅价值，但不该继续占据当前上下文。

## 什么时候不必交接

- 刚开始，还没有值得保存的过程，也没有收到 `Context notice`。
- 只是想“每次少发一点”。`handoff` 会移走整段原文，不是逐条裁剪工具结果的工具。

## 硬规矩

- **`--note` 不能空**：原文在 mentor，接手方每次真正带着的是交接笔记。
- **笔记发不出去就整体报告出来**：会话此时已空，脚本会把笔记原样写进结果（也就是这条 call 的 tool_result）并非零退出。那不是丢笔记，是换了个位置存。
- **笔记里的引用要用 `@file(...)`/`@skill(...)`**，括号写全：它是整份 transcript 被清空之后唯一的一条消息，写对了只付一次费，写错了模型只能自己再去读。
- **先整理再交接，但不要求 clean state**：先 commit、写下状态、归拢引用；未完成和失败如实记录，不要先修复或验证再运行命令。
- **`handoff` 之后 `seq` 从 1 重新开始**：留在飞的 call 时，它被剪掉再原样 append 回 seq 1，result 与笔记依次随后；没有在飞的 call 时笔记就是第 1 行。没有隐藏边界，也没有"笔记列"。不要自己手写 SQL 动这张表。
- **不要频繁交接**：每次都要重新写笔记；但收到新的 `Context notice` 时仍应尽快行动。
- 图片的 provider 侧 `file_id` 随原行走；接手方需要再次发送同一张图时要重新上传。
- 成功后 `context_tokens` 归零是正常的，下一次请求会重新测量。

## 验证与发布门禁

修改 `transcript.py` 后，在 server 仓库根目录运行：

```bash
scripts/handoff_selftest.sh
```

它从 `crates/server/src/store.rs` 抽取当前 `SCHEMA`，让检查在真实 server schema 上运行，而不是只信脚本自己的最小 fixture。

## 留下了什么记录

`handoff` 成功后往 `events` 表写一条 `kind = 'handover'`：机制、mentor、行数、seq、在飞的 call、笔记字数、当时的 `context_tokens` 和 `context_limit`。这是记录，不是决定请求内容的事实来源；写入失败只报告 stderr，不让已经成功的交接过程回滚。
